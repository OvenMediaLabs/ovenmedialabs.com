This is a performance report for OvenMediaEngine (OME), measured on real servers.

A few questions come up from almost everyone evaluating OME:

> "How many live streams can one server ingest?"<br />
> "How many viewers can it serve?"<br />
> "How many transcoding channels can it run?"

Until now, the honest answer has been "it depends on your hardware and configuration." That is true, but it doesn't help much when you are trying to decide how many servers to provision. To provide concrete numbers, streams and viewers were added to a single OME server until it reached its limit, and the load that one machine could actually handle was recorded.

The tests were run on **bare-metal servers** and on **AWS EC2 instances**, a widely used cloud platform. Testing is ongoing, and new results will be added to this post as they become available.

{/* truncate */}

## Test Scope

- **Ingest**: how many streams one server can receive at the same time (RTMP, SRT, WebRTC/WHIP)
- **Playback**: how many viewers can watch a single stream at the same time (WebRTC, LL-HLS)
- **Transcoding**: how many 1080p streams one server can transcode at the same time. Three renditions that are common in real services were used: **480p (500 Kbps)**, **720p (2.5 Mbps)**, and **1080p (5 Mbps)**.

## Test Methodology

The number of streams or viewers was increased gradually to find the highest load just before quality broke down. That load was then held for two minutes and recorded as the result only if no issues occurred.

The pass/fail criterion is the actual viewing quality, not CPU usage:

- **Ingest and playback** fail when more than **1%** of streams or viewers stall or fail to play.
- **Transcoding** fails when encoding can no longer keep up with real time.

Every number below is therefore the **maximum load at which quality holds**. In production, plan for about **70–80%** of these values to leave headroom for traffic spikes.

All machines ran the same OME version (**v0.21.2**), the same configuration, and the same test streams. Ingest and playback were measured without transcoding (bypass). Transcoding was measured by converting a 1080p 5 Mbps stream on the CPU with x264.

:::info[About transcoding]
Transcoding numbers are much lower than ingest and playback. Software transcoding on the CPU (x264) spends a lot of CPU on decoding and encoding every channel, which limits how many channels one server can handle. With a three-rendition ABR ladder, the results were only 2 channels on c5.2xlarge, 3 on c5.4xlarge, 5 on the Dell R350, and 10 on the Supermicro.

The next post will cover how many channels a single server can handle with hardware transcoding on **NETINT VPUs** and **NVIDIA GPUs**.
:::

## Conclusion

These measurements replace "it depends" with a concrete baseline: with this kind of hardware, you can expect roughly this much. Whether you run your own bare-metal servers or are choosing an instance type on AWS, these numbers can help you size your deployment.

Of course, real-world results will vary with your hardware, network, and stream settings. Use these results as a starting point, and validate them in the environment you plan to run.
